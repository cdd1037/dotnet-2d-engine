# Two-room playable slice

## Run

```sh
dotnet build managed/GameAuthoringLab.csproj -c Release
LD_LIBRARY_PATH="$PWD/build:$PWD/.deps/sdl-install/lib" \
  dotnet managed/bin/Release/net10.0/GameAuthoringLab.dll --room-demo
```

WASD/arrows move. E picks up the nearby cell; F drops it; T uses a nearby highlighted door. F5 saves to `two-room-save.json`; F9 loads it. Mouse wheel zooms. Escape exits. The player uses a bounded 60 Hz fixed step and axis-separated AABB collision with two rectangles; no general physics engine is implied.

The cell preserves its world affine transform and persistent identity at pickup/drop. A carried cell is owned by and parented to the persistent player. Room transitions destroy the previous room fixtures. A dropped cell in an inactive room is retained as an invisible persistent object with an explicit logical room index, then restored to its room on return. This is a deliberately small one-item example rather than a general streamed-world cache.

## Deterministic CLI scenario

```sh
GameAuthoringLab --scenario --save-file test-save.json
GameAuthoringLab --validate-save test-save.json
GameAuthoringLab --room-demo --load-file test-save.json --frames 120
```

Add `--headless` for contract/simulation-only testing. It validates registered BMP assets but does not upload textures or draw. `--validate-save` does not require a native graphics context. Unknown/missing resources, invalid state, malformed data and incompatible sample collision geometry reject before replacing a live game. Errors from file loading include the path; JSON syntax/type errors include field path, line, byte column and cause.

The scenario moves using the same fixed-step controller, hits an obstacle, picks up the cell, crosses rooms, drops it, saves, and reloads with the same persistent GUIDs and distinct new runtime IDs. Software rendering runs the scenario under JIT and NativeAOT. Separate processes load the resulting files for restart verification.

## Rendering and ownership

`gal_draw` is an additive 56-byte ABI command: full 2×2 affine basis, translation, local extents, color, and an opaque texture handle. Existing `gal_sprite` remains supported. Texture0 retains the built-in circle. Adjacent same-texture commands are grouped; alpha order is never changed by texture sorting. Explicit sprite layers are stably ordered before extraction. The legacy axis-aligned view rejects textured/rotated commands instead of silently dropping their transform.

Real BMP loading uses SDL, RGBA conversion and GPU upload. Files are bounded before decoding: DIB header>=40, dimensions1..4096 and file size<=70MiB. Context-owned handles are capped at256, never reused during the process, rejected after release or context replacement, and cannot be released during an active batch. Room asset synchronization preflights paths, rolls back newly uploaded resources on failure, then releases obsolete assets. Destruction waits for GPU work before releasing the context's remaining resources.

Art is original, reproducible procedural BMP data in `assets/`, generated by `scripts/generate-room-assets.py`; runtime does not need Pillow or fonts. No game code, assets or compatibility layer is inherited from another engine.

## JSON boundary

The current version1 JSON is a **runtime world/game snapshot**, containing scene/entity persistent GUIDs, separate parent/owner/scene references, affine transform data, sprite resource keys/layers and explicit game progress. Resources are referenced, not embedded. It uses a source-generated serializer and semantic validation, including uniqueness, existence, cycles, numeric limits and a512-level relation-depth bound. Behaviors are not serialized as arbitrary CLR code.

Room layout, collision rules and the asset catalog are still ordinary explicit C# for this sample. This is not yet a complete authored-level interchange format or an editor-ready arbitrary-game document. Keep the first implementation plain JSON with necessary versions and reference validation. JSON is the intended canonical authoring direction; any future compressed/binary output would be derived, and is not implemented here.

AI-driven authoring is the primary workflow. Standard shaders, explicit data and reproducible CLI checks take priority over inventing a DSL. A future visual editor may edit the same canonical formats and operations, preserving stable identities and agreed metadata; it must not introduce a separate hidden source of truth. No editor or generic extension framework is built in this milestone.

## Validation boundary

Real software Vulkan rasterization/readback verifies BMP transparency,90-degree rotation, ordered texture runs, alpha/camera/resize and both room scenes. It is Mesa CPU rendering through SDL's offscreen surface. Physical keyboard/mouse, displayed windows, physical-GPU performance, speaker output, Windows/D3D12 and Metal remain unverified. Source standard GLSL and HLSL are retained; current tested binary shaders are Vulkan SPIR-V.

The renderer fails visibly if an active room asset disappears unexpectedly; cleanup still runs. Hot-reload or transactional rollback of an entire already-committed room transition is outside this minimal slice.
